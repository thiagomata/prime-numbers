# Chapter 6 Sieve Sequence Architecture

This package has several names that sound almost identical. That is not ideal,
but the split is intentional: Stainless proofs need different objects for the
mathematical meaning, the executable gap-cycle representation, and the bridge
proofs between them.

The short version:

| Surface                    | Role                                | What it should be used for                                                             |
|----------------------------|-------------------------------------|----------------------------------------------------------------------------------------|
| `SpecSieveSequence`        | Linear-scan specification           | Define the mathematical stream of accepted values and prove spec-level facts.          |
| `CycleSieveSequence`       | Concrete gap-cycle representation   | Store a head and a positive gap cycle, then replay it through `CycleIntegral`.         |
| `SpecDerivedSieveSequence` | Canonical bridge from spec to cycle | Build a trusted cycle from spec-certified gaps and prove cycle/spec correspondence.    |
| `SpecDerivedBySurvivors`   | Survivor proof lane                 | Prove next-stage survivor facts by value-level filtering over the canonical bridge.    |
| `SpecDerivedEquivalence`   | Transfer wrapper                    | Show the canonical bridge and survivor proof lane are talking about the same cycle.    |
| `SieveSequenceNextLevel`   | Transition helper module            | Compute and prove facts about residue/expand/filter/gap/rotate transition helpers.     |
| `SieveSequenceProperties`  | Generic cycle properties            | Prove basic facts about any `CycleSieveSequence`, such as positivity and monotonicity. |
| `SieveSequenceByPrimes`    | Legacy raw-list helper              | Avoid for new proofs; use typed stage objects instead.                                |

## Why There Are Multiple Sequence Shapes

`SpecSieveSequence` is the source of meaning. It scans consecutive natural
numbers from the current head and accepts exactly the values that pass the tail
prime filters. It is deliberately plain: no stored gap cycle, no rotation, no
residue sorting, no operational shortcut. That simplicity is what makes
soundness, completeness, monotonicity, period, and counting theorems expressible.

`CycleSieveSequence` is the executable shape. It stores the current head and a
finite `GapCycle`, then generates values by replaying that cycle through
`CycleIntegral`. This is the representation a fast sieve step wants, but the
constructor can only enforce local structural facts. By itself it does not prove
that a given gap cycle is the canonical sieve gap cycle for the stored primes.

`SpecDerivedSieveSequence` closes that gap for proofs. It starts from a
`SpecSieveSequence` plus a certified period, derives the spec gap cycle, and
packages the resulting `CycleSieveSequence`. Because the cycle is built from the
spec, the bridge may freely use spec facts to prove the cycle emits the same
values.

`SpecDerivedBySurvivors` exists because one next-stage proof route is easier at
the value level than through old index machinery. It wraps the canonical bridge
and proves that filtered cycle survivors match the next spec filters. It is not
a fourth semantic model; it is a proof lane over the same derived cycle.

`SpecDerivedEquivalence` is a small transfer object. Its job is to certify that
facts proved through the survivor lane and facts proved through the canonical
bridge refer to the same head, modulus, gap cycle, and generated values.

## The Next-Stage Transition Surfaces

The historical pain point is `SieveSequenceNextLevel`. It contains many methods
whose names start with `next`:

```text
nextResidues -> nextExpanded -> nextFiltered -> nextSorted ->
nextGaps -> nextHeadResidueIndex -> nextRotatedGaps
```

These names are implementation stages, not separate definitions of a sieve
sequence. They describe one residue-based construction of a finite next gap
cycle:

1. enumerate current tail-filter residues modulo the current tail primorial,
2. lift those residues through a window of length `head * modulus`,
3. remove values divisible by the current head,
4. sort the finite residue representatives for gap calculation,
5. calculate wrap-around gaps,
6. rotate the gaps so the next head is the cycle origin.

The same file also contains walk/window helpers such as `collectGaps`,
`nextGapsWalk`, `currentWindow`, and `survivorWindow`. Those helpers are a
different implementation/proof lane: they scan values generated by the current
cycle and filter survivors directly. Tickets record that direct proofs about
`nextGapsWalk` have timed out several times, so the current code keeps explicit
side-by-side lanes instead of pretending there is one clean transition theorem.

## Current Proof Boundary

The useful mental model is:

```text
Spec meaning
  -> canonical cycle derived from spec
  -> survivor/filter proof lane
  -> concrete transition helpers
```

Counting and period facts should normally start in `SpecSieveSequence`, because
the spec talks about ordinary integer candidates and the acceptance predicate.
The residue pipeline is useful for concrete construction and local helper
facts, but previous work showed that driving global count proofs through
`nextSorted`, `nextFiltered`, or `nextGapsWalk` creates brittle verifier work.

The package therefore has more names than a clean final design would want. When
adding new facts, first decide which layer owns the statement:

- semantic stream or count theorem: `SpecSieveSequence`;
- concrete gap-cycle storage or replay: `CycleSieveSequence`;
- spec-to-cycle correspondence: `SpecDerivedSieveSequence`;
- survivor/filter bridge for the next stage: `SpecDerivedBySurvivors`;
- residue/expand/filter/sort/gap/rotate helper facts: `SieveSequenceNextLevel`;
- generic cycle-sequence facts: `SieveSequenceProperties`.

If a theorem seems to need several of these at once, it is probably a bridge
theorem. Make that bridge explicit instead of hiding it behind another
similarly named helper.

## Legacy Raw-List Helper

`SieveSequenceByPrimes` is old scaffolding. It gives raw `List[BigInt]`
versions of `head`, tail filters, modulus, and acceptance, but it does not carry
the `AllPrimesSoFarList` invariants that current proofs normally need. It also
has no active source callers in this package. New proofs should start from
`SpecSieveSequence`, `CycleSieveSequence`, or an explicit bridge object instead
of adding more facts to `SieveSequenceByPrimes`.
